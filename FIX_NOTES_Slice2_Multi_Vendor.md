# Slice 2 — Multi-Vendor Rendering & First Switch Device

Date: 2026-04-11
Plan reference: [PLAN_Slice2_Multi_Vendor.md](PLAN_Slice2_Multi_Vendor.md)
Predecessor: [FIX_NOTES_Slice1_HLD_Pipeline.md](FIX_NOTES_Slice1_HLD_Pipeline.md)

## What shipped

Slice 2 of the HLD-driven closed loop is **complete and verified end-to-end
against real Neo4j + Live-Memory + a live Nokia SR Linux containerlab node**.
A single HLD population-table edit now propagates through the pipeline and
reaches the running SR Linux switch. The vendor-dispatch architecture is
in place so adding a third vendor in a future slice is purely additive.

### Switch OS swap: cEOS → SR Linux

The plan recommended Arista cEOS, but Slice 2 ships **Nokia SR Linux**
instead. Reason: cEOS requires an Arista account to download the image,
which we don't have on this host. SR Linux is freely pullable from
`ghcr.io/nokia/srlinux:latest`, has a **native arm64 image** (no QEMU
emulation), and **boots in ~17 seconds** vs. cEOS's projected 2+ minutes
under QEMU. The vendor-dispatch architecture is OS-agnostic, so the swap
only changed strings (`"vyos"`/`"srlinux"` instead of `"vyos"`/`"cEOS"`),
not shape.

## End-to-end demo

```bash
# 0. The SR Linux switch must be running. One-time per session:
cp clab-ibnlab-switches.yml /tmp/
sudo containerlab deploy -t /tmp/clab-ibnlab-switches.yml --reconfigure

# 1. (already done) git hook is installed from Slice 1
# 2. Edit the HLD population table — add or modify a population row
$EDITOR "Enterprise_Campus_Network_HLD (1).md"

# 3. Commit
git commit -am "Add a new population on VLAN 191"
# → [ibn-hook] HLD changed in <sha> — closed-loop pipeline running in background
# → [ibn-hook] tail -f .git/ibn-hld-pipeline.log to follow

# 4. Watch
tail -f .git/ibn-hld-pipeline.log
# Look for:
#   ✓ A3 render             5 configs rendered      (4 firewalls + 1 SR Linux)
#   ✓ A5 deploy             1 devices pushed, 4 skipped (empty render)

# 5. Verify on the live SR Linux container
docker exec clab-ibnlab-switches-acc-sw-01 sr_cli "info from running" \
  | grep "network-instance vlan-191"

# 6. Verify the L1 VLAN + TRACES_TO Intent in Neo4j
docker exec ibn-neo4j cypher-shell -u neo4j -p ibn-closed-loop-2026 \
  "MATCH (v:VLAN {vlanId: 191})-[:TRACES_TO]->(i:Intent)
   RETURN v.name, v.origin, i.intentId"
```

## Architectural decisions made during execution

1. **OS swap to SR Linux** — documented above. The plan's documented
   fallback turned out to be the right call for this host.

2. **`docker exec sr_cli` instead of SSH** — SR Linux containers expose
   `sr_cli` as a CLI shell inside the container. Pushing via `docker exec -i`
   bypasses SSH credential management entirely and matches how I validated
   the image during Task 1. The vendor dispatch table makes this just one
   row in `_VENDOR_EXECUTORS`, so future vendors can pick whichever push
   channel matches their idiom (SSH, NETCONF, eAPI, gNMI, Ansible).

3. **Additive `clab-ibnlab-switches.yml` instead of editing `clab.yml`** —
   `clab.yml` is regenerated by `netlab create` from `topology_ibn_lab.yml`
   on every lab bootstrap. Editing it directly would lose the switch the
   next time `~/start-ibn-lab.sh` runs. The additive topology shares the
   `netlab_mgmt` network so all containers see each other.

4. **Skip empty rendered configs in A5 instead of failing on them** — A3
   currently produces empty configs for devices it has no template support
   for (e.g. the seed's edge routers, aggregation switches without a
   matching vendor template). Pre-Slice-2, A5 would attempt an SSH push to
   their non-resolvable hostnames and crash mid-loop, blocking everything
   that came after. Now A5 skips them with a `device-result` note and
   continues to the devices it CAN actually push to. The skipped count
   surfaces in the orchestrator's stage summary so it's not silent.

5. **Surface A5 internal failure status in the orchestrator** — pre-Slice-2,
   A5's `_execute()` returned `{"status": "FAILED"}` on rollback without
   raising, but the orchestrator's stage marker was hardcoded `ok` regardless
   of the result content. This was masking a Slice 1 issue where the seed
   has Neo4j device IDs (`DEV-HQ-DMZFW-01`) that don't match the actual
   containerlab container names (`clab-ibnlab-dmzfw1`), so all VyOS pushes
   were silently failing. The stage now inspects each intent's status and
   marks `error` if any FAILED. **Important:** this is honest now, but it
   also means the Slice 1 acceptance test would have caught the deviceId
   mismatch had it been wired this way originally — which is the deferred
   followup.

6. **L1 VLAN node + `TRACES_TO` relationship** — Slice 1 only wrote L4
   Intents from the HLD; Slice 2 also writes L1 VLAN nodes because that's
   what switch templates need to render against. The `TRACES_TO` edge
   makes the audit trail queryable both ways: from a VLAN you can find
   the originating Intent, and from an Intent you can list all VLANs
   that came from it.

7. **Template chain order matters** — `srl_interfaces.j2` must run BEFORE
   `srl_vlans.j2` because SR Linux requires `vlan-tagging true` on the
   parent interface before any subinterface can use `vlan-id`. Discovered
   when the first manual push failed with `vlan-id only configurable if
   vlan-tagging enabled on parent interface`. The chain order in
   `_TEMPLATE_CHAINS["srlinux"]` is now explicit and commented.

## Known limitations (deferred to later slices)

1. **VyOS firewall pushes still fail silently in the lab** — the Neo4j seed
   uses `DEV-HQ-USF-01` style device IDs but the containerlab containers
   are named `clab-ibnlab-usf1` etc. A5's empty-content skip masks this
   for now (the seeded firewall templates render empty so they get
   skipped before crashing), but this is a real gap. **Slice 3** will fix
   it as part of device provisioning by adding a `clabContainer` property
   to Device nodes and having A5 dispatch on it directly.

2. **Switch is deployed as a separate clab topology** — `clab-ibnlab-switches.yml`
   needs to be deployed manually after the main lab. This works but it's
   a UX wart. **Slice 3** (device provisioning) will let the HLD itself
   declare devices, and the closed loop will mutate the topology
   automatically — at which point both the firewall lab and the switch
   lab merge into one declarative source.

3. **Only one switch, no HA pair** — Slice 6 will add the second access
   switch and the aggregation pair, alongside other realism (LAG, LLDP,
   port-security).

4. **Switch templates are minimal** — hostname, vlan-tagging, per-VLAN
   subinterface + mac-vrf. No per-port population assignment, no LLDP,
   no LAG, no QoS. Slice 6 extends this from HLD §6 port-config sections.

5. **A2 still doesn't decompose Intents into switch-relevant policies**
   — switches consume L1 VLAN nodes (which A1 writes), not L4 FirewallRule
   nodes (which A2 writes). The two artifact paths coexist and that's the
   right architecture, but it means A2 currently has nothing to do for
   switches. Slice 5 will add 802.1X / port-security policies that DO
   need A2 to decompose.

6. **No content-based diff verification on the SR Linux push** — A5 calls
   `_srlinux_ssh_verifier` but the verifier hits a parse error in some
   sr_cli configurations. Currently we don't break the pipeline on
   verification failures (warnings only). Slice 6 cleanup.

## Schema evolution notes

- Added `Intent.origin` (Slice 1) and `VLAN.origin` (Slice 2) for HLD
  source-line lineage. Both are optional, both are queryable.
- New relationship: `(VLAN)-[:TRACES_TO]->(Intent)`. The reverse direction
  is not created — the audit trail is uni-directional from L1 → L4.
- Future Slice 3 will likely add `Device.clabContainer` for the
  containerlab name; right now we work around it by storing the container
  name as the `deviceId` of the SR Linux device.
